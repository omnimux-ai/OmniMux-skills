# 商品套图

商品套图是一组连续回答购买问题的图片系统：第一张负责点击，后续图片负责理解、相信、比较和下单。

这是一个公开业务 skill。它的公开入口只依赖本目录中的方法说明、提示、schema、模板、样例和静态配置。

## 公开边界

- 只负责商品套图规划、单图职责拆解、风格规则、提示词交接和整套图质检。
- 不承诺自动抓取商品页、自动读取外部平台内容、自动生成最终图片、自动上传平台或自动交付素材包。
- 不把固定工具顺序、固定阶段机、provider 路由、隐藏 workflow 或完成门禁写进 skill 入口。
- 是否调用工具，取决于当前请求、可见工具 schema、输入完整度和可见执行结果。

## 适用场景

- 用户要做电商 Listing 图片套系、主图和副图。
- 用户有产品卖点但不知道每张图该承担什么任务。
- 用户需要把同一产品扩展成多张风格一致的商业图片。
- 用户需要把产品 brief、商品链接、已有素材或参考图转成图片生成 prompt pack。
- 用户需要诊断一套商品图是否重复、缺少关键购买信息或风格不统一。

## 不适用场景

- 用户只要复刻某一张参考图。
- 用户只要 A+ 长页面或品牌故事。
- 用户要视频脚本、视频提示词或视频生成。
- 用户只要普通海报、插画、社交卡片或信息图。
- 用户要求像素级复制他人品牌图、竞品包装、平台徽章、认证章或受保护资产。

## 输入要求

- 产品信息、图片、卖点、参数和目标平台。
- 目标用户、使用场景、价格/定位和竞品差异。
- 图片数量、比例、风格和禁用表达。
- 已有素材的可用状态：产品图、包装图、Logo、场景图、用户评价、检测报告或资质证明。
- 合规边界：不能使用的词、不能暗示的功效、不能出现的品牌或竞品元素。

## 任务模式

| 模式 | 用户目标 | 输出边界 |
| --- | --- | --- |
| `listing-plan` | 定义整套图顺序、每张图职责和转化逻辑。 | 输出套图策略和图片矩阵，不承诺生成最终图片。 |
| `shot-plan` | 规划主图、场景图、卖点图、细节图、对比图、规格图。 | 输出每张图的画面、构图、素材和文案说明。 |
| `prompt-pack` | 把每张图转成生成提示词或设计说明。 | 输出可交给图像生成工具或设计师的 prompt pack。 |
| `set-review` | 检查整套图是否重复、缺口、风格不统一或卖点不清。 | 输出问题清单、优先级和修改建议，不自动改图。 |
| `variant-plan` | 为多颜色、多规格、多平台生成套图变体。 | 输出哪些元素可变、哪些产品识别点必须保持一致。 |

## 能力包结构

按任务需要读取根目录支持材料：

- `docs/usage.md`：套图工作方法、输入节奏和图片顺序建议。
- `docs/compliance-notes.md`：电商表达、对比、认证、效果承诺等风险边界。
- `docs/export-guide.md`：审核版、交付版、平台上传版的导出注意点。
- `docs/naming-conventions.md`：文件、版本和交付物命名建议。
- `prompts/`：输入收集、规划、单图说明、质检和总提示框架。
- `schemas/`：输入、风格规范、套图计划和输出包的结构参考。
- `templates/`：主图、卖点图、场景图、细节图、对比图、规格图和收尾图模板。
- `examples/`：校准样例，只用于理解输出形态。
- `config/resolutions.json`、`config/safety-rules.json`：尺寸偏好和风险检查清单。

## 输出合同

- 整套图策略和图片顺序。
- 每张图的目标、画面、文案、素材需求。
- 统一视觉规则和变体控制。
- 生成提示词、负向约束和验收清单。
- 必要假设、缺失信息和合规风险提示。
- 如果用户只要求诊断，不升级成生成任务；如果用户要求生成，先给可执行 prompt pack，再由独立工具能力决定是否继续执行。

## 质量检查

- 第一张图必须清楚呈现产品和点击理由。
- 每张副图必须解决不同购买疑问。
- 整套图必须统一产品外观和视觉风格。
- 不得用夸大或无证据表达替代真实卖点。
- 产品颜色、材质、结构、数量、Logo 和包装不得在不同图片之间漂移。
- 对比图只能基于可验证事实，不贬低竞品，不使用未授权的竞品品牌资产。
- 功效、认证、排名、销量、奖项和用户反馈必须有用户提供的证据；没有证据时改写为场景、材质、规格或使用体验描述。

## 运行边界

- 本 skill 只提供上下文，不得强制固定 workflow、固定阶段机、provider 路由、工具选择或完成门禁。
- 是否调用工具取决于当前用户请求、输入完整度、权限和工具 schema。
- 如果输入缺失，只问会改变输出的最小澄清问题；否则声明假设并继续。
- 区分分析、创作、转换、变体规划和交付移交；不要在用户只要求分析时升级成生成任务。
- 如果用户要求最终出图，先交付可执行的 prompt pack 和验收清单，再由独立工具能力决定是否继续执行。
