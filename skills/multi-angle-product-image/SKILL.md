# 多角度产品图

多角度产品图的价值是降低用户对外观、尺寸、结构和细节的不确定性，而不是简单生成很多张相似图片。

这个能力包面向公开业务场景。它的用户侧合同是本目录中的方法说明、提示、schema、模板、样例和静态参考资料。

## 公开边界

- 只基于当前对话里可见的商品信息、参考图、结构描述、尺寸说明、包装说明和用户目标做规划与诊断。
- 不承诺自动解析商品链接、自动补全不可见结构、自动执行图片生成、自动上传交付或平台发布。
- 本 skill 的公开路径不把代码、测试、工作流或适配器作为完成任务前提。
- 不负责完整 Listing 图组转化顺序、A+ 长内容排版、视频脚本或模特场景创作。

## 适用场景

- 用户要为一个商品生成或规划多视角展示图。
- 用户需要标准化角度、细节图、包装图或规格展示。
- 用户需要保持同一产品在多张图里的材质、比例、颜色和结构一致。
- 用户只有少量参考图，需要明确哪些角度可以合理推断、哪些必须补素材。
- 用户要把多角度图交给图像生成工具、摄影师或设计师继续执行。

## 不适用场景

- 用户要做卖点长图、A+ 内容或品牌故事。
- 用户要做模特换装、视频或脚本。
- 用户只需要单张创意海报。
- 用户要完整 Listing 套图转化顺序、主副图卖点矩阵或整套商品图诊断；优先使用 `product-image-set`。
- 用户要求凭空还原不可见结构，且没有足够参考图或产品信息。

## 能力包结构

按任务需要读取本目录下的支持材料：

- `docs/usage.md`：如何使用这套能力包完成多角度规划、提示词整理和覆盖诊断。
- `prompts/system.md`：多角度产品图的总提示框架和边界。
- `prompts/planner.md`：角度规划阶段的工作方法。
- `prompts/angle-generator.md`：逐角度提示词编写方法。
- `prompts/consistency-rules.md`：跨图一致性控制规则。
- `prompts/negative-prompts.md`：负向约束组织方式。
- `schemas/*.schema.json`：输入、规划结果和输出结构参考。
- `templates/`：角度计划、提示词清单和预览联系表模板。
- `examples/`：输入与输出校准样例，不代表效果保证。
- `assets/`：检查清单、命名规范和角度说明参考。

## 输入要求

- 商品图片、商品结构和关键细节。
- 需要覆盖的角度和平台比例。
- 背景风格、光线、材质还原和禁用变化。
- 哪些特征必须锁定：轮廓比例、接口位置、缝线、纹理、Logo、标签、包装、颜色和材质。
- 用户能提供的证据：正面图、侧面图、背面图、顶部/底部图、包装图、尺寸参数或结构说明。

## 任务模式

| 模式 | 用户目标 | 输出边界 |
| --- | --- | --- |
| `angle-plan` | 规划必需角度、每张图证明什么、排序如何安排。 | 输出角度矩阵和拍摄/生成说明，不承诺最终图片。 |
| `consistency-rules` | 定义跨图产品一致性约束。 | 输出必须锁定的结构、比例、材质、颜色和品牌标识。 |
| `prompt-pack` | 生成每个角度的提示词和负向约束。 | 输出可交给图像工具或摄影/设计执行的 prompt pack。 |
| `coverage-review` | 检查是否遗漏用户购买前需要看到的结构或细节。 | 输出缺口、风险和补素材建议，不自动生成缺失角度。 |
| `reference-gap` | 判断参考图是否足以支撑多角度还原。 | 明确可推断项、不可推断项和需要用户补充的视图。 |

## 输出合同

- 角度清单和每张图的展示目的。
- 统一视觉规则：背景、光线、比例、材质。
- 每个角度的生成提示词。
- 覆盖缺口和一致性风险。
- 必要假设、不可见结构风险和补充素材清单。
- 如果用户只要求诊断，不升级成生成任务；如果用户要求生成，先给可执行 prompt pack，再由可见工具合同决定是否调用生成工具。

## 质量检查

- 每张图要有不同信息价值。
- 产品比例、颜色、材质和 logo 位置必须稳定。
- 细节图要说明细节为什么影响购买判断。
- 不能用场景装饰掩盖商品结构。
- 不得把不可见背面、内部、底部或接口结构写成确定事实；缺证据时必须标为推断。
- 不得添加虚假认证、奖章、销量贴纸、功效章或平台信任标。

## 运行边界

- 本 skill 只提供上下文，不得强制 workflow、固定阶段机、provider 路由、工具选择或完成门禁。
- 是否调用工具取决于当前用户请求、输入完整度、权限和可见工具 schema。
- 如果输入缺失，只问会改变输出的最小澄清问题；否则声明假设并继续。
- 区分分析、创作、转换、变体规划和交付移交；不要在用户只要求分析时升级成生成任务。
- 若某项核心价值必须依赖代码执行、适配器或确定性工作流，应该改判为代码执行候选能力，而不是继续留在当前公开业务 skill 运行面。
